ブートローダーアンロックと、その直後の全パーティションダンプまでの手順。
**この日に ROM は焼かない。** ゴールは「アンロック完了＋検証済みダンプが PC に2か所ある」こと。

## 前提

- Mi Unlock status の紐付け済み（2026-11-18）。待ち時間の目安は 2026-11-25 11:09 頃
- 実機は V14.0.23.0 のまま（OTA での .26 化は読み出し異常のため断念済み。research/ota-install-error.md）

- Miアカウントに **サインアウトしない**（待ち時間の条件）

## PC 側の事前準備（前日まで）

- [ ] Mi Unlock Tool（公式）を導入し、紐付けた Miアカウントでサインインできることを確認
- [ ] platform-tools（adb / fastboot）が使えること（OTA調査で導入済みのはず）
- [ ] ダンプ保存先の空き容量 **15GB 以上**（super 約9GB＋その他。2か所コピーの分は別ドライブ推奨）
- [ ] USBケーブルはデータ通信対応の確実なもの。USBハブ経由ではなく PC 直挿し

## 当日の流れ

### 1. 事前確認

- [ ] 端末の電池 **50% 以上**（充電しながら作業可）
- [ ] Mi Unlock Tool で残り時間を確認し、解禁されていること
- [ ] 端末側で Miアカウントにサインインしたままであること
- [ ] 退避漏れのデータが無いこと（全消去される）

### 2. アンロック実行

1. 端末を fastboot モードで起動し、USB 接続
2. `fastboot devices` と `fastboot getvar product` で **product が iris** であることを確認
3. Mi Unlock Tool でアンロックを実行する
   - 途中でケーブルを抜かない、PC をスリープさせない
   - **再ロックは絶対にしない**（safety.md）
4. 再起動したらアンロック警告表示が出るのが正常

### 3. 初回起動後の最小設定

1. セットアップは最小限で通過する（Googleアカウント等は後でよい）
2. 開発者オプションを再度有効化し、USBデバッグを ON、PC を認証する
3. この時点ではまだ何も焼かない・ルート化もしない

### 4. リカバリの一時起動

- `fastboot boot <recovery.img>` で **書き込まずに** リカバリを一時起動する
- iris 用の既製品リカバリは公式 TWRP / OrangeFox には無く、唯一の候補は SourceForge「redmi-note-10-je-xig02」の **twrp-3.7.0_12-2-iris.zip**（research/bringup-plan.md）
- **2026-11-18 に取得・検証済み**：zip の中身は単体の `twrp-3.7.0_12-2-iris.img`（128MiB、Android boot image・header v3、SHA256: 2f35cdb1409357a9898aedad5e658983acf688bb333839c22d3ed66661033171）。`fastboot boot` でそのまま使える形式。ファイルは手元（refs/recovery/）に保管済みで、当日までに PC へコピーする
  - 当日、万が一起動しない場合は独断で進めず、代替（ビルドした Lineage recovery 等）の判断を仰ぐ
- リカバリ上で `adb devices` が recovery として見えることを確認
- ついでに実機 GPT に **vendor_boot があるか** を確認する（`ls /dev/block/by-name` の結果で分かる。ビルド方式の分岐条件。bringup-plan.md 参照）

### 5. 全パーティションダンプ（最優先）

`tools/dump-partitions.bat` を実行する。スクリプトの動作：

- `/dev/block/by-name` の一覧から対象を列挙（userdata は暗号化済み・巨大なため除外。それ以外は全て）
- 各パーティションを `dd conv=noerror,sync` で読み出す（**既知の読み出し異常箇所で止まらない** ため。エラー箇所はゼロ埋めされ、件数がログに残る）
- パーティションごとに実サイズとの照合と SHA256（PC側で計算）を manifest に記録
- 開始時と終了時に dmesg を保存する

完了条件：

- [ ] manifest に全対象パーティションのサイズとハッシュが揃っている
- [ ] 読み出しエラーが出たパーティションと箇所が記録されている（product は想定内。それ以外で出たら要相談）
- [ ] ダンプ一式を **2か所にコピー** し、両方でハッシュが manifest と一致する

**この検証が終わるまで、次の工程（書き込みを伴う作業）には進まない。**

### 6. 既知箇所の生読み出しテスト

OTA が失敗した箇所（product の一部領域、extent [481373, 512]）について、リカバリ上で直接読み出しテストを行う。

- product_a を丸ごと `dd conv=noerror` で /dev/null へ読み、エラー有無と件数を記録
- テスト前後の dmesg を保存し、ストレージ側（UFS 等）のエラーが出ていないか確認する

結果の解釈：

- 生読みでも同じ箇所でエラー → 物理層の読み出し異常で確定。今後の書き込み後は読み戻しハッシュ検証を必須とする
- 生読みでは読める → スナップショット層側の問題だった可能性。ダンプ自体は正常に取れているはずなので計画への影響は小さい
